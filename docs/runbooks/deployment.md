# Deployment runbook

## Signal

A merge to `main`, a release pull request, or an explicit need to publish a new
build.

## Preconditions

- The pull request is green in `.github/workflows/ci.yml` (validation and
  Playwright jobs).
- `npm run bundle:check` passes locally if dependencies changed.
- `npm run client-boundary:check` passes if dependencies, telemetry modules,
  or workflows changed (it runs in CI regardless).
- `npm run docs:check` passes if `package.json`, workflows, budgets, runbooks,
  or skills changed.
- A Vercel preview URL exists for the pull request.

## Steps

1. Verify the release pull request opened by Release Please
   (`.github/workflows/release-please.yml`). Read the proposed changelog; write a
   corrected commit message and push again if an entry is wrong.
2. Merge the release pull request. Release Please updates `CHANGELOG.md` and
   `package.json`, tags the commit, and publishes the GitHub Release.
3. Watch the Vercel production deployment for the merge commit. The build is
   `npm run build` with output `dist`.
4. Open the production URL and confirm:
   - the provider selector defaults to the local mock;
   - the Home KPIs render and the fiscal phase toggles switch quarters;
   - the Forecasting week-over-week chart draws the current quarter.
5. In DevTools, confirm no unexpected warning or error records. Production
   defaults to `warn`; successful loads need not appear in the console.
6. Only if approved transport and the master telemetry switch are enabled,
   use the configured `VITE_TELEMETRY_DASHBOARD_URL` to verify technical release,
   provider, error, and health events. The URL alone does not enable collection.
   Default builds remain local-only; inspect
   `await window.GTM_HEALTH.refresh()` instead. No collector is connected here.
7. If the repository is public or has a GitHub plan supporting private Pages,
   optionally publish GitHub Pages
   by running `.github/workflows/deploy-pages.yml` via `workflow_dispatch` and
   selecting the current `main`. Never run it from a private Free-plan repo; the
   deploy step fails with a 404.

## Base path

`vite.config.ts` chooses the asset base from the environment: `/` when `VERCEL`
is set, `/GTM-Partner-Dashboard/` otherwise. Set `BASE_PATH` to override for any
other host. A blank page with 404s on `/assets/*` is almost always a base-path
mismatch.

## Confirming success

- The production deployment shows the merge commit SHA.
- The GitHub Release exists with the expected version and notes.
- No new error-level log records appear in the first minutes of traffic.

## If something is wrong

Follow [`rollback.md`](./rollback.md). Do not edit `dist/` by hand; it is
regenerated by the build.
